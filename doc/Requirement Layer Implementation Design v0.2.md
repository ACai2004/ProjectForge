# Requirement Layer Implementation Design v0.2

> 状态：Implementation Design（初步实现设计，非最终架构、非生产级平台设计）
> 版本：v0.2（基于 v0.1 的聚焦修订）
> 上游约束：Requirement Layer Blueprint v0.1（概念层） + Requirement Layer Workflow v0.2（用户人工定稿，工作流层）
> 技术底座：Claude Agent SDK
> 定位：把已确定的需求层工作流，转换成一套「足以开始实现 MVP」的系统设计。
>
> 本版相对 v0.1 的变更（仅限以下三项，不重设整体结构，不扩大 MVP 范围）：
> 1. **Review 机制**：由「无独立 Review Agent」调整为「轻量独立 Review capability（单次 Review Subagent）」。限定在 Candidate Definition → Human Confirmation 之间；只检查忠实 / 诚实 / 越界 / 明显一致性；无自动批准、无多轮、无复杂治理流程。它与先前被否决的「独立 Review Agent 编排 / 多轮纠错 / 自动审查门」不是同一个东西（见 §3.3）。
> 2. **Working Summary**：由「纯流动（不持久化）」轻量提升为「工作摘要工件」，仅在实质认知转折点更新；同时服务跨会话恢复与 Review 忠实性检查的输入（见 §4.3 / §6）。
> 3. **Research Tool 边界**：维持单一通用研究工具；明确「被接受的研究结论进入 Working Summary（带来源）」，原始研究过程留在对话（见 §4.2 / §5-D）。
>
> 其余结构、结论、MVP 边界维持 v0.1 不变。本次不为「完整感」扩大设计范围。
>
> 设计态度（沿用）：
> - 这是初步设计。允许保留未决问题、给出多个候选方案、暂不决定细节、标记未来再解决。
> - 不引入已被否决的设计：五态状态机、复杂 Baseline 生命周期、复杂 delegation / authorization 框架、多层多轮 Review、Research 执行子代理编排、工作流引擎、复杂数据库模型。
> - 概念模型 ≠ 数据模型。本文档做职责与边界的分析；除 MVP 必须的最小约定外，不做 schema、字段、目录命名等最终定案。

## 1. Design Goal

**一句话**：用 Claude Agent SDK 实现一个「单一主 Agent 驱动的 Requirement Layer」——人用自然语言输入一个模糊的项目意图，系统通过对话完成探索、按需研究并把发现带回讨论、在人的决策点形成候选定义、经一次独立视角的轻量检查,再由人确认后固化为持久化的 Project Requirement Baseline，并支持跨会话延续与显式修订回环。

**成功判据**（对应 Workflow §17 最小可靠闭环）：
1. 一个真实项目能走通：模糊意图 → 探索（↕研究）→ 定义 → 候选定义 → 人确认 → Baseline。
2. 一条回路成立：Baseline 被新信息挑战 → 人判断 → 重探索 → 新 Baseline。
3. 人不会被要求「对每一句话确认」；Agent 不会在未经确认时把候选当决定。
4. 候选形成时有一次**独立视角**的轻量检查，产出发现材料供人参考，但不代替人确认、不阻塞。
5. MVP 小到真正能跑起来（边界见第 9 节）。

**非目标（第一版明确不做）**：自动 Review Agent 编排与多层多轮审查、Research 子代理、委托/授权框架、多项目并行管理 UI、复杂版本管理与 diff 工具。

## 2. System Responsibilities

按「必须存在 / 可交给 Claude 原生能力 / 可先人工 / 第一版不需要」四分。

### 2.1 必须由系统承载
| 职责 | 说明 |
|------|------|
| 对话式探索推进 | 理解、追问、质疑、比较、重构；不问卷（Workflow §4.3） |
| 维护「当前项目理解」 | 会话内流动认知；在实质转折点沉淀为 Working Summary（非权威） |
| 研究触发与执行 | 判断何时需要外部证据 → 检索/读取 → 组织发现 |
| 研究返回纪律 | 发现 → 解释与当前定义的关系 → 回到讨论，不自动进基线（§5.2/5.3）；被接受后记入 Working Summary（带来源） |
| 起草候选定义 | 从已讨论内容归纳；每条带确认位置与一句话来源；不自行补全（§6.2） |
| 轻量独立可信性检查 | 候选形成后调用 Review capability，产出忠实/诚实/越界/一致性发现材料（§3.3） |
| 确认接收 | 接收人的确认/修正并更新候选（§9） |
| Baseline 固化 | 人确认后写入持久化当前定义 + 版本/修订记录（§12, §13.1） |
| 跨会话恢复 | 以项目句柄载入当前 Baseline + 草稿 + Working Summary，继续项目 |
| 失败路径最小集 | 人不收敛→不强制；暂停→草稿保留；矛盾→指出不猜测（§16） |

### 2.2 可交给 Claude 原生能力
- 语言理解、提问、总结、重构（模型固有，不工具化、不建库）。
- 发现矛盾、识别被忽略的假设（推理能力）。
- 会话内「当前项目理解」的流动主体（对话上下文承载；摘要只是其轻量沉淀）。

### 2.3 第一版可先由人工完成
- Baseline 的最终签收（人本身就是确认者，无需额外装置）。
- 跨会话恢复的入口（人说出「继续项目 X」→ Agent 载入）。
- 项目目录/项目名的创建（Agent 建议，人确认即可）。

### 2.4 第一版不需要
- 权限、多用户、协作。
- 多层 / 多轮 / 自动批准的 Review 体系（本版引入的是**单次、无批准权**的轻量 capability，见 §3.3）。
- 委托 / 授权框架（Workflow §18 明确第一版不解决）。
- 工作流引擎 / 复杂状态机 / 复杂编排层。
- Baseline 生命周期状态体系（Active/Suspended/Pending/Dead——§13.1 明确禁止）。
- 项目类型识别与档位配置流程（§15 明确禁止三档流程）。

## 3. Proposed Agent Architecture

### 3.1 判断：第一版一个主 Agent 足够

理由：
1. 需求层的本质是「一个持续对话里的认知形成」。探索中的每一句都是候选定义的潜在原料；拆出多个 Agent 只产生昂贵的上下文移交和「谁代表当前项目理解」的歧义。
2. 三个核心状态（Exploration / Definition / Baseline）是**认知模式**，不是进程边界。同一 Agent、同一对话内切换模式即可；把它们映射成不同 Agent，会把「模式」错误物化成「阶段角色」。
3. 可信性检查由轻量独立 Review capability 承担（生成独立视角的发现材料）；主 Agent 不自行做「自检通过」判断，最终裁决仍是人。**主 Agent 与 Review 的分离只在候选形成这一个点发生**，不改变「对话全流程单主 Agent」的判断。

### 3.2 Research：第一版不拆独立 Subagent，作为主 Agent 的工具能力

分析：
- 独立 Research Agent 的价值：研究占用大量 token/工具调用、可能污染对话流、可并行开展。
- 成本：发现需回灌主对话（上下文移交成本）；增加编排复杂度；显著放大 MVP 工作量。
- **第一版折中**：研究 = 主 Agent 的一个工具（检索/读取 → 摘要 + 来源 → 组织成「发现 + 与当前定义的关系」返回对话）。「研究是否影响定义」的判断始终由主 Agent 与人一起做——这一判断无论拆分与否都跑不掉，独立 Agent 只省执行、不省认知。
- 留作未来开关：若真实使用中研究变重（长检索、大批量文献），把「研究**执行**」拆成 Subagent，「研究**结果解释**」留主 Agent。Workflow §18 已将此列为第一版不解决。

### 3.3 Review：轻量独立 Review capability（单次、非审查门）

**本版引入点。** 与先前被否决的设计做显式区分：

| 维度 | 被否决的「独立 Review Agent」 | 本版「轻量 Review capability」 |
|------|------------------------------|-------------------------------|
| 运行时机 | 各阶段、多环节 | 仅 Candidate Definition → Human Confirmation 之间，一次 |
| 检查内容 | MISS / EXTRA / ERROR 量化、多维度 | 忠实 / 诚实 / 越界 / 明显一致性（Workflow §8 的原三问 + 一致性） |
| 运行轮次 | 多轮自迭代纠错 | 单次；候选被修订后不默认重跑（人修订视为人在审；仅人要求时才可重跑，非默认流程） |
| 输出 | 通过/不通过、质量分 | 发现材料（供人参考的条目清单），无结论、无评分 |
| 权力 | 可把关/门禁 | 无自动批准权、不阻塞——是否接受发现、是否确认仍由人 |
| 定位 | 替代人审 / 防错基础设施 | 提供一个与生成者不同的视角（生成者有自我解释偏差，同上下文重读难以发现自己把假设写成事实） |

**形状**：一个单次调用的轻量 Review Subagent（**新上下文**，只读输入）。
- **输入**：候选定义文件 + Working Summary（忠实性检查的对照基准）+ 审查范围指令。
- **检查范围（严格限定）**：忠实（已谈定的关键项是否遗漏/歪曲）、诚实（假设是否写成事实 / 推断是否写成人的决定 / 未知是否写成确定）、越界（是否把技术方案写进问题定义）、明显一致性（候选内部、以及与当前 Baseline 的矛盾）。**不评价方向好坏、不核查外部事实、不重新解释研究来源。**
- **输出**：发现材料条目，交回主 Agent 如实呈现给用户。
- **为什么新上下文**：独立性是它存在的唯一理由。若共享主 Agent 上下文，等于「换一层皮的自检」，自我解释偏差会复现。

### 3.4 架构图（概念层）

```
┌──────────────────────────────────────────────────────────────┐
│  Main Agent（单主 Agent：对话驱动全流程）                         │
│  · 探索推进 / 模式切换（探索↔定义）/ 研究触发与解释                │
│  · 候选定义起草 / 确认接收 / Baseline 落盘 / Working Summary 维护 │
│    (在实质认知转折点)                                          │
│                                                                │
│  ├─ skill: requirement-layer（Workflow 的行为化规范）           │
│  ├─ 研究工具（外部检索 → 发现摘要 + 来源 + 关系标注）             │
│  ├─ 标准文件工具（读材料 / 写草稿 / 写读 Baseline / 摘要）        │
│  ├─ Session → 项目目录（跨会话恢复）                            │
│  └─ Review Subagent（单次、候选点运行）                          │
│      输入：候选 + Working Summary → 输出：发现材料 →            │
│      交回主 Agent 呈现给 Human（无批准权、不阻塞）              │
│                                                                │
│  主对话只有一个 Agent。Review 是候选点的一次性独立检查。          │
└──────────────────────────────────────────────────────────────┘
```

## 4. Skill / Tool / Artifact Responsibilities

### 4.1 Skill：承载「怎么做」——把 Workflow 行为化

一个主 skill（`requirement-layer`）将 Workflow 的认知原则变成 Agent 在会话中的行为准则：

| 工作流条目 | Skill 行为化 |
|-----------|-------------|
| 探索不问卷（§4.3） | 按「当前什么最值得澄清」推动下一轮讨论；不按固定清单走 |
| 暗示性小结 | 仅在出现实质认知变化 / 方向级转折 / 人要求时才给小结（探索收盘参考），不按轮次定时、不催促收敛 |
| 研究纪律（§5） | 触发需说明理由与要回答的问题；返回必标注与当前定义的关系；未接受结果不得写进候选/Baseline；被接受后其结论写入 Working Summary（带来源） |
| 起草规则（§6.2） | 只从「已讨论且已形成」的内容归纳；每条带确认位置（已确认/暂定/未解决/有意推迟）与一句话来源；缺口不自行补全 |
| 三问检查（§8） | 在候选点调用轻量 Review capability（见 §3.3）；主 Agent 如实呈现全部发现材料、不遮蔽、不替 Review 下「通过/不通过」结论；由人裁定 |
| Working Summary 维护 | 仅在实质认知转折点（方向级变化 / 已定项产生 / 研究被接受）更新摘要；它不是权威，Baseline 才是权威 |
| 确认纪律（§12, §13.1） | 未经人确认不进 Baseline；新 Baseline 确认前旧 Baseline 仍有效；修订显式记录 |
| 比例原则（§15） | 不设档位；同一套原则按对话自然深度伸缩——探索深度/研究次数/整理粒度/确认粒度自动适应 |

**为什么一个 skill 而非拆三个**：三个核心状态是同一认知体的不同姿态，拆成独立 skill 会碎片化「什么已谈定」的共享判断，并增加切换成本。Workflow 已删除「档位/阶段」概念，skill 对应保持单一。skill 内部的组织（是否分子文件）属实现细节，可再调。

### 4.2 Tool：承载「不能靠纯对话完成」的动作

- **研究工具**（第一版一个通用形态即可）：检索/读取外部信息 → 返回结构化发现（要点 + 来源 + 与当前方向的关系标注）。不做多个专业研究工具（论文/代码/网页各一个）——MVP 用通用能力足够。
  - **边界（轻量调整）**：原始检索过程与未接受的发现留在对话（不持久化）；**被接受的研究结论**由主 Agent 写入 Working Summary，附来源引用，作为后续候选/基线中「依据」条目的出处。研究工具本身不改动任何项目工件。
- **标准文件工具**（读/写/编辑文件）：读用户材料；写候选草稿；写读 Baseline；读写 Working Summary。
- 注意：Agent 的思考、提问、总结不需工具化（原生能力）；矛盾识别不需工具化。

### 4.3 Artifact：承载「必须跨对话存活」的信息

持久化难度分层（不是 schema，是边界判断）：

| 内容 | 载体 | 理由 |
|------|------|------|
| Baseline 当前版 + 历史版本 + 修订记录 | **必须持久化 artifact** | 权威定义、可回溯（§13.1） |
| 候选定义草稿 | **应该持久化 artifact** | 防打断丢失、跨会话恢复；未生效、非权威 |
| Working Summary（项目认知工作摘要） | **应该持久化 artifact（轻量）** | 跨会话恢复入口 + Review 忠实性检查的对照基准；非权威 |
| 研究发现 | 对话承载（原始过程）；被接受结论写入 Working Summary/候选（带来源） | 未接受不落盘；被接受必须留下来作依据 |
| 探索叙述、研究全过程、Agent 中间推理 | 对话上下文（不持久化） | 流动层合法随会话流逝（§1 核心定位） |

**收束原则**：Artifact 只负责三类内容——「确认后必须留下」（Baseline / 历史 / 修订）、「被打断不能丢」（候选草稿 / Working Summary）、「供审查复核的依据」（Working Summary 作为忠实性对照）。其余随对话流逝是合法的。

## 5. Runtime Interaction Flow

按用户指定 A–L 以「系统行为」叙述（不重复 Workflow 文档）。

**A. 模糊想法进入**
人建会话、表达想法/给材料。Agent 识别为新项目意图，按 skill 先理解再推进，不要求填字段。建议为项目起名并建立项目目录（含空 Working Summary），人可接受或忽略。

**B. Exploration**
Agent 以对话回合推进：理解→追问→质疑→比较→提候选方向。可能读取用户材料。当前项目理解在会话上下文中累积；出现实质认知变化时，同一触发点同时给出暗示性小结（在谈什么 / 候选方向 / 可能影响方向的未决）并更新 Working Summary。不催收敛。

**C. Research 触发**
两条源：人要求；或 Agent 判断「对话解决不了 / 需验证已有工作 / 方向是否成立需查证」。Agent 先陈述理由与要回答的问题 → 提议研究（不擅自长时间离场）→ 人同意或直接派发。随后调用研究工具。

**D. Research 返回**
工具返回发现。Agent 组织成「要点 + 来源 + 关系标注（支持当前 X / 威胁 Y / 无关 / 启发 Z）」回到对话。**系统行为关键点**：研究结果是新的认知输入，不是新决定；Agent 视其为讨论原料，未被接受不写进任何项目工件。被接受后，其结论写入 Working Summary（带来源引用），作为候选/基线「依据」条目的出处。

**E. 方向变化**
研究或讨论表明可能推翻已确认内容时，Agent 显式声明「这可能改变我们先前确认的 X」，指出受影响条目，停等。人不确认则不变。回环无需新 session / 新 agent——同一对话内从「定义姿态」或「稳定姿态」回到「探索姿态」。

**F. Definition**
由人示意（「差不多可以固化了吧」）。Agent 切换姿态：停止发散，在会话内列出「已谈定的」候选清单（不直接落到最终措辞）。确认 Working Summary 已反映当前已谈定状态（为起草与审查提供同一基准）。

**G. Candidate Definition**
Agent 起草候选定义草稿（写草稿文件，防丢失）。每条标注：内容、确认位置（已确认/暂定/未解决/有意推迟）、一句话来源。不含探索噪声、不自行补缺口。随后**调用轻量 Review Subagent**（输入：候选 + Working Summary；检查：忠实 / 诚实 / 越界 / 明显一致性；输出：发现材料，无结论）。主 Agent 将候选与发现材料一并呈现给用户，不遮蔽、不替 Review 下「通过」结论，并把「请特别注意」的项高亮（哪条是假设、哪条可能越界、有无漏掉）。

**H. Human Confirmation**
人审阅候选 + Review 发现：可整体接受、逐条修改、把某条退回讨论、把某条标为暂定。Agent 每轮更新草稿。人的确认最小表达是对话中的一句肯定；不做结构化打分/逐条点选。候选中需要改动的条目若人认可 Review 发现，按人的意见修订即可，不默认重跑 Review（修订由人在审）。

**I. Baseline 形成**
人最终确认后，Agent 把草稿提升为当前 Baseline（持久化，标记版本与时间，指向依据来源）。该文件成为此项目此后会话的权威定义来源。

**J. Baseline 被挑战**
后续（本项目任何会话、或技术阶段反馈）出现可能影响方向/范围/成功条件的新信息。Agent 明确指出其影响的特定条目，不静默修改。高级行为：Agent 区分「实现方法不行」（技术问题，不触碰 Baseline）与「问题定义本身存疑」（需求层议题，进回环）。

**K. 重新进入 Exploration**
人判断影响属实 → 同一项目回到探索姿态。**旧 Baseline 不作废、不标记暂停——它仍是当前有效定义**（§13.1），只是有新认知在酝酿。Agent 围绕新信息探索，逐步可能产出新的候选定义（与旧基线对照）。

**L. 新 Baseline**
新候选 → 人确认 → 新 Baseline 版本。修订记录显式列出「相对上一版改了什么、为什么」；旧内容留在历史版本，不删除。

**A–L 之后的系统行为要点**（超出上次版新增一条）：
- 三种认知姿态（探索 / 定义 / 基线的审查与修订）在同一会话内由角色切换实现，不是进程或 Agent 切换。
- 所有「已确认内容被改动」都经由「人判断 → 新版本确认」，没有静默路径。
- 人只在真正的决策点被请停（进定义 / 方向变化 / 确认 / 挑战判定）；探索与研究执行不频繁打断。
- **Review 发现是确认时的参考材料，不是新打断点**——它发生在确认点之前、被主 Agent 并入确认材料呈现；不阻断确认，最终仍由人。

## 6. State / Context / Artifact Model

概念区分（不是 schema）。同时回答「Session / Context / Persistence 在概念上分别解决什么问题」。

| 概念 | 是什么 | 解决什么 | 持久化？ |
|------|--------|---------|---------|
| 当前对话上下文（Context） | 本次会话内 Agent 可见的全部信息（对话历史 + 读入工件内容） | 当前判断的依据 | 否（随会话结束） |
| 当前项目理解 | Agent 对「项目现在是什么」的认知：全量流动于对话上下文；轻量结构沉淀于 Working Summary | 探索与定义共享的「已谈定什么」的认知 | 全量否；轻量摘要版是 |
| Working Summary（工作摘要） | 当前方向、已定/暂定要点、影响方向的未决、候选与研究接受状态（带来源） | 跨会话恢复入口 + Review 忠实性检查的对照基准；非权威 | 是（轻量文件，实质点更新） |
| 候选定义（Candidate） | 一份「准备交人确认」的定型表述，带确认位置与来源标注 | 确认动作的对象 | 草稿文件（可恢复，非权威） |
| 已确认 Baseline | 权威定义 | 跨会话的项目真实性 | 是（当前版 + 历史 + 修订记录） |
| 研究发现（Research Findings） | 原始过程活于对话；被接受结论写入 Working Summary/候选（带来源） | 讨论后的认知输入，接受的成为依据 | 原始否；接受结论随摘要/候选 |
| Decisions / uncertainty | 每条内容的「确认位置标注」（已确认/暂定/未解决/有意推迟），文本级 | 让不确定性被正确表达而非消灭 | 随候选/Baseline |
| 历史 revision | Baseline 既往版本 + 修订记录 | 可回溯与显式变更记录 | 是 |
| **Session** | 一次对话运行单元 | 一次使用期间的连续上下文与工具能力 | —（自带，不承载项目真实） |
| **Context** | 某一时刻 Agent 可用信息窗口 | 当前判断依据，可跨会话重建（读入工件） | — |
| **Persistence** | 跨会话信息保持 | 项目在会话之间不丢失其真实 | 文件系统承载 |

**一句话分工**：Session 是运行单元，Context 是推理窗口，Persistence 是项目真实所在。**Requirement Layer 的可信性来自 Persistence（Baseline 持久且经人确认 + Working Summary 带来恢复与审查基准），而不是 Session 的连续性**——这正是「文件即真相 / 不依赖模糊对话记忆」在实现面的体现。

第一版持久化最小集合：一个项目目录（含当前 Baseline、历史/修订记录、候选草稿、Working Summary），足够。布局留实现。

## ｜ Sources与 Agent 的边界（Human-Agent）

### 7.1 Agent 自主（不打断人）
- 探索内推进：理解、追问、质疑、比较、提候选。
- 研究执行与建议研究。
- 候选草稿、调用 Review capability 并如实呈现发现材料。
- 归纳、总结、改写候选。
- 维护 Working Summary（仅在实质认知转折点）。

### 7 2 必须停等的人决策点（完整清单，维持 v0.1 五个）
1. 进入 Definition（Agent 只建议，§11）。
2. 方向 / 核心范围 / 重大取舍 / 成功条件（Agent 只建议，§10.2）。
3. 研究结论挑战已确认项：是否接受（§5.3）。
4. 候选定义是否确认 → 是否形成 Baseline（§12）。
5. Baseline 被威胁时：是否重新探索（§13）。

> Review 发现**不新增打断点**——它只是决策点 4（确认）时的参考材料，由主 Agent 一并呈现；人看完材料后按既有决策路径走。

### 7.3 不可自动做的事
方向、边界、核心取舍、成功条件、放弃 / 收窄 / 重定义——即使 Agent 有强建议，也没有「定为决策」的权限。Review capability 同样没有——它的发现不被视为「审查通过」证明，不构成形成 Baseline 的必经门。与 Workflow §18 对齐：**第一版不做委托/授权框架**，因此以上决策点一律人工。减少打扰只能在真实使用暴露「哪些点其实可免问」之后考虑，且不可重引入静默授权。

### 7.4 Confirmation 最小表达
人对话中一句「可以 / 就这样 / 第三项改成 X」即算确认或修正；MVP 不做结构化确认 UI。候选呈现时主 Agent 高亮「真正需要注意的项」（假设、未决、越界嫌疑，含 Review 发现），让人不必逐句细读也抓住关键决策。

### 7.5 避免过度打断
- 决策点清单即全部打断源；探索内默认 Agent 连跑多轮。
- 研究触发前只问一次（「我去查 X？」），不反复追问。
- 暗示性小结只在实质认知变化时出现，不按轮次定时。
- Review capability 单次运行，不在候选修订后默认重跑（人修订由人在审）。

## 8. Baseline Management

- **建立**：候选定义经人确认 → 提升为当前 Baseline（v1）。
- **后续版本**：每次人确认的新候选 → 新版本；修订记录显式列变化与理由。
- **旧版本**：留存历史。旧内容不删除、不假装仍有效由「当前版本指针」负责——「当前有效」指向最新已确认版，旧版保留但明确标注为非当前。
- **挑战期间**：旧 Baseline 保持有效（§13.1），直到新版本被确认。**不引入** suspended/pending/dead 等生命周期标志。
- **技术阶段回环**：技术反馈属「实现方法不行」→ 不触 Baseline；属「问题定义存疑」→ 走人判断 → 重探索 → 新版本（§14）。
- **防静默修改**：所有对当前 Baseline 的改动经由「候选 → 人确认 → 新版本」通路；直接编辑当前文件不构成合法变更。
- **Review 与 Baseline 的关系**：Review 发现不自动进入 Baseline——只有人采纳其意见并走确认流程后，变化才落地；Review 的存在不改变 §13.1 的生命周期语义。

## 9. MVP Scope

### 9.1 Must Have（能跑通最小闭环）
1. 一个主 Agent + `requirement-layer` skill（探索/研究返回/起草/Review 调用/确认纪律/摘要维护规则）。
2. 对话式探索，无问卷；暗示性小结。
3. 一个研究工具（检索 + 摘要 + 来源 + 关系标注）与研究返回纪律。
4. 候选定义起草（写草稿文件）。
5. **轻量 Review capability**（单次 Subagent：输入候选 + Working Summary；输出忠实/诚实/越界/一致性发现材料；无自动批准、无多轮）。
6. **Working Summary**（轻量文件，实质点更新；支持恢复与作为 Review 输入）。
7. 人确认（对话内，接受 / 修正）。
8. Baseline 固化（当前版 + 版本/修订记录的最小结构）。
9. 跨会话恢复（读当前 Baseline + 草稿 + Working Summary，继续项目）。
10. 失败路径最小集：人不收敛→不强制；中途退出→草稿保留；说法矛盾→指出不猜测。

### 9.2 Useful but can wait
- Review 发现的持久化存档（当前随确认结束即丢，人需要时可让 Agent 记入讨论记录）。
- Baseline 版本的人读 diff。
- 候选定义模板丰富化（先极简）。
- 探索小结的自动累积视图（Working Summary 已是最轻的雏形，可视化可后置）。

### 9.3 Clearly out of scope（第一版）
- 独立 Research Subagent（研究执行拆出）。
- 多层 / 多轮 / 自动批准的 Review 体系（单次轻量 capability 是 MVP 内边界）。
- 委托 / 授权框架。
- 多用户 / 权限 / 协作。
- 工作流引擎 / 复杂状态机 / 复杂编排层。
- 复杂数据库模型（文件系统足够）。
- 全项目类型统一抽象 / 类型检测引导。

## 10. Deferred Questions

（承接 Workflow §18，落到实现层；本版因 Review 与 Working Summary 调整，补充两项）

1. Research 的执行形态：主 Agent 内 vs 独立 Subagent——重研究场景出现后再定。
2. Baseline 文件格式与版本组织（单文件多版本 / 多文件 / 目录）——MVP 先最简，运行后调整。
3. 确认度标注是否结构化（目前为文本标注）。
4. 跨会话恢复的入口 UX（人如何表达「继续项目 X」最顺）。
5. **Working Summary 的详细结构与更新频率边界**——MVP 先用最简形态（方向/已定暂定/影响方向的未决/候选与研究接受状态），运行后按实际需要调整。
6. 长期暂停 / 搁置后如何恢复流动认知（Working Summary 只能恢复结构化层，全量流动认知随会话不可恢复——若真实使用中丢失严重，再考虑更厚的中间摘要）。
7. **Review capability 的强度与边界演进**：目前严格单次、无批准权；是否未来扩展到更形式化的检查（目前禁止自动批准/多轮），以及候选大改后是否重跑，留真实运行验证。

## 11. Key Design Risks

1. **探索早熟收敛 / 候选当决定**：Agent 语气与 skill 行为需明确「探索不自行结束、提示不以确认口吻」。兜底 = 决策点强制人停。
2. **研究沦为背景检索**：检索结果未被呈现、未被接受就影响后续推断；或被接受后未写入 Working Summary，导致恢复与审查时研究结论漂移。skill 强制「返回 → 标注关系 → 回讨论 → 被接受才记录」；未接受不得进工件。
3. **草稿 / Working Summary / Baseline 三层边界模糊**：Working Summary 与草稿都是非权威、可改的，Baseline 才是权威。边界规则：摘要只在实质点更新（不随探索流走）、草稿只在定义点产生（只归纳不添加）、权威只在人确认后落 Baseline。防「摘要被当权威」的头注与纪律写入 skill。
4. **跨会话恢复漂移**：恢复时 Agent 把「自己的理解 + 摘要」与「Baseline 原文」混淆。恢复动作明确「Baseline = 权威、摘要 = 非权威上下文、对话理解 = 可推翻」。
5. **比例原则回滑成档位**：不引入档位选择流程（§15 红线）；深度由对话自然决定。实现时警惕「加个快捷开关」的诱惑。
6. **MVP 蔓延**：用第 9 节明确的 out-of-scope 清单拦截。
7. **Review capability 滑向自动批准或多轮**：护栏写死在 skill——单次、无结论输出、发现即材料、修订不默认重跑。真实运行若暴露「需要更强检查」，需先经人决策再放宽，不能由实现自行加门。
8. **Review 的「独立性」退化**：若实现时图省事让 Review 共享主 Agent 上下文，等于「换一层皮的自检」，自我解释偏差复现。护栏：新上下文 + 只读输入（候选 + 摘要 + 指令）。
9. **Working Summary 被误当权威**：下游（人或未来技术层）可能只读摘要。护栏：文件头注明确「非权威，以 Baseline 为准」。

## 12. Implementation Design Confidence

**已经比较稳定（可据此直接开写 MVP）**：
- 单一主 Agent + 单点轻量 Review capability 的架构判断（对话全流程单主 Agent，候选点新增一次独立检查）。
- 研究 = 工具能力 + 返回纪律 + 被接受结论写入工作摘要（「研究融于探索」的实现方式）。
- 持久化边界（Baseline / 版本 / 草稿 / Working Summary 为 artifact；对话与推理为上下文）。
- 5 个必须停人的决策点清单（Review 不新增打断点）。
- Review capability 的「发现材料、无批准权、单点、单次」定位（新上下文保证独立性）。
- 旧 Baseline 在挑战期间保持有效（无生命周期状态）。

**仍然是假设（实现时需轻验证）**：
- Review capability 采用独立 Subagent 的实际成本与收益（vs 若成本过高，退回同上下文「换视角重读」提示——但需明确接受独立性下降）。
- 一个主 skill 承载全部模式行为是否顺滑（vs 按模式拆内部结构）。
- 研究工具用通用搜索形态（vs 多种专用能力）。
- 候选草稿文件 vs 对话内成稿（草稿文件是否真的必要）——取决于真实会话被打断的频率。

**最好等 MVP 实际使用后再决定**：
- Baseline 文件格式与版本组织策略。
- 确认度标注是否结构化为字段。
- Research 是否值得拆独立 Subagent。
- 跨会话恢复的 UX，以及 Working Summary 的结构是否需要加厚（补充流动认知）。
- Review capability 的强度是否值得放宽（目前禁止自动批准/多轮），由人决策后再演进。
- 是否出现确实值得引入委托的过度打断点（届时再议，第一版不做）。
