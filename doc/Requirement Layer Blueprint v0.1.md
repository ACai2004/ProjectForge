# Requirement Layer Blueprint v0.1

> 状态：Conceptual / System Design（概念架构层，非代码、非 Skill、非字段设计）
> 版本：v0.1 — Red-Team 修订版
> 定位：把「从模糊项目意图到稳定项目定义」的过程，设计成一个可运行的认知系统。
>
> 本次修订基于对 v0.1 初稿的一次 Red-Team Self-Review。修订要点：
> 1. 新增**比例原则**（治理重量随不确定性与复杂度调节）——评审发现初稿对小型项目过度工程化；
> 2. 三层信息模型压为**两层**（流动 / 稳定=Baseline）；
> 3. 撤回「失效标记 dead」，合并进「Baseline 修订记录 + 版本史」；
> 4. 五个确定状态压为**一条确认度轴 + 溯源 + Assumption 验证路径**，不设五个平级对象；
> 5. 「唯一输入契约」弱化为「唯一正式项目定义基线（权威定义），依据史可回溯」；
> 6. Review 压缩到**第一版最小集**，MISS/EXTRA/ERROR、独立审查、多轮纠错、来源标签强制标注为「以后加」；并明确**探索阶段无对照基准、Review 思维停用**；
> 7. 责任边界增加「用户可显式委托 Agent 自主决定」；
> 8. 12 维与 7 判据**降级为候选/示例/提问倾向**，并显式承认其与「Unknown 合法」的张力。
>
> 本文档刻意停留在：模式 / 阶段 / 核心信息维度 / 状态 / 责任边界 / 输入输出 / Gate / Review 原则。
> 刻意推迟到后续：Python/TypeScript、Agent 数量、Skill 文件、Prompt、API、JSON Schema、数据库、目录结构、Markdown 模板。
> 尤其注意：**本文档不该把任何概念模型读成数据表或持久化结构。**

## 0. 一份诚实的注记（读本文档前请先看这里）

本 Blueprint 的参考对象是 PM（OpenClaw 企业产品 PRD）项目。撰写前我对照了 PM 项目**真实设计文档与真实运行日志**，得到一个直接影响本设计的结论：

- 我把 PM 的**设计文档**（P1–P5 五阶段、13 环节、独立 Review Subagent、MISS/EXTRA/ERROR 量化、3 轮自迭代）与**真实运行日志**（quick_start intake + 直接生成 + 人审循环）区分对待。
- 实证显示：**保证 PM 系统可靠性的，不是「自动化的 Review Subagent」，而是「人作为最终审查者、对每个影响结果的变更先看计划再拍板」这一循环。** 设计文档里的自动化 Review 机制，在这批日志中找不到独立运行证据。
- 因此本 Blueprint 的一个明确取向：**可信性的锚点是人，自动化是辅助。** 价值在于「提供一个与生成者不同的视角」，绝不以「自动审查通过」替代「人确认」。

**另一份诚实的声明（来自本次 Red-Team）**：初稿在三个地方过度工程化（三层信息模型、五态确定模型、Review 防错架构）、一个地方表述过强（唯一输入契约）、一个地方严重缺失（比例原则）。本次修订针对这五点做了削减与补全。

## 1. Requirement Layer 定位

**一句话**：需求层是把「流动的、模糊的项目认知」逐步稳定成「可被后续技术阶段可靠消费的项目定义」的过程治理层。

它**不是** PRD Generator（目标不是产出文档），**不是**需求收集表单（目标不是填满字段），而是：

> 帮助人把一个尚未稳定的项目想法，通过探索、讨论、研究、质疑、收敛、确认，变成一个**明确、诚实、稳定、边界清晰、可进入技术阶段**的项目定义的过程。

它在整个生命周期中的位置：

```
模糊项目意图
   ↓（自由对话 + 研究，认知是流动的）
【需求层：探索模式 ⇄ 定义模式】
   ↓（人对方向与范围盖章）
【Project Requirement Baseline —— 需求层的产物】
   ↓（技术阶段以其为权威定义来源）
技术研究 → 技术设计 → 实现 → 验证 → 演化
```

核心姿态：**文档是结果，不是目的；目的是形成可靠的项目认知。** Baseline 是这种认知在某个时点的稳定快照。

**防御性提醒（规划粒度）**：本节以下所有「模式 / 状态 / 维度 / 机制」都是**认知与职责层面**的描述，不代表它们是数据对象、文件或持久化结构。真实系统需要多少「对象」是由运行验证决定的，不由本文档决定。

## 2. 输入与输出边界

### 2.1 从哪里开始（输入）

一个项目进入需求层的**触发状态**是：人有一个尚不稳定的项目意图（可以只是「我大概想做这个」，甚至一句话）。

- **输入是什么**：人的自然语言表述 + 人可能提供的外部材料（笔记、论文、已有代码、参考链接、竞品信息）。这些只是**原料**，不代表「需求已成立」。
- **进入时不做的事**：不假设方向已成立，不假设「需求已经在那里等收集」，不强迫先填任何固定字段。
- **实际进入动作**：从自由对话开始，先建立「我们在谈一个什么问题」。

### 2.2 在哪里结束（输出）

可认为 Baseline 「已形成」的判定，是**一组稳定感判据**（是「感觉是否稳定」的提示，不是「必须逐条勾选」的门槛，也不是量化打分）：

1. 核心问题与方向已被明确表述，且经过讨论（方向性歧义已解决，或已显式列为 Open Question）；
2. 边界已建立：做什么 / 不做什么 / 现在不研究什么 / 有意推迟什么；
3. 成功条件已有一个可被理解从而验证的表述；
4. 不确定已被**分层诚实表达**（哪些确定、哪些暂定、哪些未知），——不以「全部填成确定」作为结束条件；
5. 概念契约（关键术语/概念定义）已稳定到不会在阶段间漂移；
6. 剩余 Unknown 落在「可接受、可验证、有验证路径」的范围，且方向歧义已解决；
7. 人已对上述内容**显式确认**（盖章）。

> ⚠️ **张力声明**：判据 6（要求 Unknown 基本落在可验证范围）与「Unknown 可以合法存在」存在潜在地张力。判据 6 **不应被当作「凑齐未知就放行」的硬门**——它只是提醒「当方向歧义与不可解未知仍大量存在时，谈基线可能过早」。尤其对研究型项目，过早稳定本身是错误。真正生效的是第 9.4 节的「诚实表达」，而不是凑齐这些判据。

### 2.3 属于需求层的事

- 理解意图并推进思考（追问、质疑、比较、重构）。
- 外部研究，并把研究结论**先带回讨论、再由人判断它是否改变定义**（研究本身可以是需求层的一部分，见第 4 节）。
- 帮助项目从模糊逐渐收敛：提出问题、澄清、显式化假设、建立边界、定义成功。
- 建立概念契约（命名稳定）。
- 把确定项与不确定项分层，忠实表达。
- 把最终形成的认知沉淀为 Baseline，并守护它不被无声修改。

### 2.4 明确不属于需求层的事（边界）

| 不属于 | 理由 |
|--------|------|
| 具体技术选型（框架、语言、数据库、服务拆分） | 属于技术阶段；需求层只定义「问题空间」，不预决「解空间」。 |
| 详细系统架构 / 模块拆分 / 类与接口设计 | 技术设计阶段的职责。 |
| 具体代码实现 / 部署方案 | 再后续的阶段。 |
| 把「自动生成最终代码」当作需求层存在的理由 | 代码生成的真正价值是「证明认知可可靠传递」，不是需求层的目的本身。 |

### 2.5 四个相邻概念的一条边界梳理

- **探索**：需求层内最开放的模式（发现可能性、提假设、研究、让方向出现）。
- **需求定义**：需求层内收敛的模式（从已探讨内容中挑出「确定下来」的、固定下来）。
- **技术研究**：需求层结束后，为「如何实现」做研究（不改变「做什么」，只探索「怎么做」的可行性）。
- **技术设计**：把确定的问题空间落到具体方案。

**关键边界**：需求层结束后进入技术研究/设计时，若发现「问题定义本身需要改」，应**显式回环**到需求层（见第 4 节），而不是默认需求层无效。**如何区分「技术研究发现的必要问题重定义」与「技术研究在正常推进」**——这条分界目前没有确切判据，属于 Open Design Question 3，本文档不断言它有边界清晰答案。

## 3. 核心认知过程

一个项目在需求层内，认知应该经历这样一个变化（这里是**认知状态**的变化，不是流程步骤）：

```
我大概想做这个（模糊意图）
   → 我在解决什么问题？这个方向成立吗？
   → 有没有已有工作？有没有更好的问题定义？（研究 + 讨论）
   → 我们到底决定做什么？做到什么程度？
   → 哪些已确定？哪些是假设？哪些仍未知？
   → 当前是否足够稳定，可以进入技术阶段？
```

对应的根本转变：**项目从「我大概想做这个」，逐渐变成「我们明确知道现在要做什么、为什么这样做、不做什么、哪些已知哪些未知」。**

关键点：这条路径**不是单向直线**。研究可能把方向拉回「这个问题定义错了」，于是回到更早的状态重新讨论。需求层必须允许这种**再次流动**，但要求流动是「显式的」（被记录、不污染已确认的东西）。

## 4. 探索与定义的关系

这是需求层最重要的结构设计。

### 4.1 探索是否属于需求层

**属于，而且是需求层的前端主体。** 对一个方向的未定型想法，「探索」（自由讨论、研究、质疑、让新方向出现）不是可有可无的前置闲聊，而是「让项目本身形成」的必要过程。定义阶段的产出质量，取决于探索阶段是否让方向真正想清楚了。

### 4.2 探索与定义是两个不同模式

是。它们不是两个阶段时间点，而是两种**认知姿态 / 模式**：

- **探索模式**：允许改变项目。重点是发现、讨论、研究、质疑、重构、容忍矛盾与未定。产物是**流动的**（对话、研究笔记、待定假设、候选方向），可增删改，不作为正式输入。
- **定义模式**：必须忠实于已确认的项目。重点是整理、明确、收敛、建立边界、诚实分层。产物是**稳定的**，一旦人确认，就不能被无声修改。

> 一句话：**探索阶段允许改变项目；定义阶段必须忠实于已经确认的项目。**

### 4.3 两者如何切换

切换是**人的显式授权动作**，不是 Agent 的自动判断：

- 从探索进入定义：人明确说「我觉得方向差不多了，开始固化吧 / 进入定义」。Agent 不得自己判断「聊得差不多了」而擅入定义。
- Agent 的角色是**提示**：「当前方向似乎已经足够成熟，你是否要进入定义？还剩这些 Open Question 需要继续讨论。」——但**决定权在人**。

### 4.4 定义完成后是否允许重新进入探索

**允许，且应当被支持。** 场景：定义过程中或后续技术研究中，出现了足以威胁当前方向的新信息（研究找到更优问题定义、发现原方向不成立、用户想法变化）。

- 它必须是**显式回环**：记录「因某发现，方向待重议」，而不是无声地推翻已确认内容。
- 已确认的定义**不自动作废**——如果仍有保留价值，保留并继承；只有当新方向明确取代它时，才进入「显式废弃」记录（见 4.5）。

### 4.5 重新进入探索时，原来的定义发生什么

- 原来已确认而且新的方向**仍成立**的部分 → **保留**并继承。
- 已确认但被新方向**推翻**的部分 → **在 Baseline 修订记录中显式声明「被 X 取代/废弃」**，不删除原文（保留历史与依据），也不让失效内容继续假装有效。
- 未决定的 Open Question → 继续带入新讨论。
- 新方向产生的新问题 → 新的一轮探索。

> **关于「失效标记」：经 Red-Team 复核，本次不再设立一个独立的 dead / 失效状态机制。** 「旧结论不被误当有效」这件事，由 **Baseline 修订记录 + 版本演进**自然解决：当 B 取代 A 时，一条「修订记录：A 因某依据被 B 取代」即完成任务，旧内容随版本史自然留在过去。额外造一个 dead 对象会增加治理成本而不带来增量价值。**这是本次比初稿更轻的处理。**

## 5. 候选信息维度模型（降级为「提问倾向」，非字段清单）

> **重要（本次修订）**：以下 12 个维度**不是「第一版必须填的字段」**，也不是一份 checklist。它们是**在讨论中自然值得触及的问题倾向**，用来帮助思考不要漏掉影响方向的方面。**具体某个项目可能只用到其中少数几个，其余全部不适用——这是完全合法的状态。** 按比例原则（第 11 节），小项目只需极少数维度。

**核心问题**：为了让后续技术阶段能可靠理解「我们究竟要做什么」，一个项目至少需要被谈到哪些方面？每维只标注：解决什么、后续依赖什么。

| 维度 | 解决什么 | 后续依赖 | 常适用对象 |
|------|---------|---------|-----------|
| A. 要解决的问题与动机 | 我们为什么做、真正解决什么 | 技术阶段判断方案是否对症 | 几乎一切项目 |
| B. 项目方向与目标 | 我们决定做什么方面、达到什么目标 | 一切以此为锚 | 几乎一切项目 |
| C. Actor / Context / Environment | 谁/什么在什么环境下作用或使用（不预设「产品用户」） | 理解交互对象与边界 | 有交互对象的项目 |
| D. 能力边界（做什么/不做什么） | 划定范围上下限，防蔓延 | 确定研究/实现边界 | 多数组件化项目 |
| E. 研究边界（现在不研究什么） | 显式声明当前不回答的问题 | 防止误入未授权方向 | 研究/探索型项目 |
| F. 推迟项（Deferred） | 记录「现在定不做，留条件再回看」 | 区分有意推迟与遗漏 | 有一定 scope 的项目 |
| G. 成功条件与验证方式 | 什么叫做成、怎么知道成不成 | 技术阶段设计验证 | 有「可验证结果」的项目 |
| H. 约束 | 不可违背的限制 | 选型/排期必须服从 | 有外部依赖/时间/资源限制的项目 |
| I. 核心概念与术语 | 命名稳定、定义有权威 | 后续共用同一语言 | 概念易混、需多阶段协作的项目 |
| J. 关键已有资产/上下文 | 记录已有代码/笔记/相关资料 | 决定从零做 or 改造 | 有既有积累的项目 |
| K. 中间参考材料 | 记录研究结论、讨论依据出处 | 让断言可回溯 | 方向会变、需要复核的项目 |
| L. 确定 / 假设 / 未知 总账 | 分层显式记录（见第 6 节） | 技术阶段把假设当研究起点 | 有不确定性的项目 |

> 说明：维度 I（概念契约）继承自 PM 的 glossary——**这是合法继承的原则**（术语稳定性防漂移），并非企业语义偷渡。但它在第一版**不强制**：对单人不跨阶段协作的小项目，甚至可以不列。其余维度均经重新解释，无企业 KPI / User Journey / Business Role / 灰度 / 回滚 / 跨角色影响等语义。

## 6. 确定性模型（降级为「一条确认度轴 + 溯源」，非五格数据表）

> **重要（本次修订）**：初稿把 Decision / Assumption / Unknown / Open Question / Deferred 列为「五种状态」。经 Red-Team 复核，**它们不是五个平级对象，而是一条「确认度轴」+ 少数含义各异的标志 + 溯源原则**。本文档不再把它们设计成数据表/枚举，只保留概念假设；是否在实现中成为独立对象，由运行验证决定。

### 6.1 它们各自解决什么认知问题

- **确定 **（≈ Decision）：已经人确认、后续必须遵守。**这是一条内容的「确认度最高状态」，不是独立信息类型。**
- **暂定 / 采用中**（≈ Assumption）：为推进临时采用的未验证前提——**主体是「未确认内容」，带「尚未验证」标志与验证路径/失效条件。**
- **空白 / 未知**（≈ Unknown）：知道存在但无答案。拆「已知的未知」与「未知的未知」是*思考维度的提醒*，不是两个存储槽。
- **待办 / 未决问题**（≈ Open Question）：已提出未回答。真正重要的是一个标注：**是否可能影响方向**（方向性→尽早升级给人 / 运行性→不阻塞）。
- **推迟**（≈ Deferred）：「决定现在不定，留条件再回看」——**是「确定」的一个子含义**（确认了「此刻不定」），附回归条件。

### 6.2 哪些可以合并 / 哪些不是独立类型

- **Unknown 与 Open Question 高度重叠**：「不知道答案」与「有问题待回答」往往是同一件事的两面。真正的差别只在「是否影响方向」这个**标注**，不足以分成两个独立对象。
- **Decision 与 Deferred 不同级**：Decision 是确认度轴的最高端；Deferred 是「确认：此刻不决定」这一特殊取值。二者不在同一层。
- **Assumption 只是「未确认内容」的一种状态**，不是独立类型。「五态」这种说法本身误导——真实是一条轴 + 少数标志。

### 6.3 保留为 Conceptual Hypothesis 的部分（其余暂不定案）

- ✅ **一条确认度轴**：内容要么「已确认（Decision）」，要么「采用中（Assumption）/ 留白（Unknown）/ 待答（Open Question）」，要么「推迟（Deferred 子形态）」。这是干净的最小心智模型。
- ✅ **来源可溯源**：每条关键内容应能向上追溯「人表述 / 外部资料 / 研究结论 / Agent 推断 / 已确认决策」——这支撑「不伪装确定性」与「可复核」。
- ✅ **Assumption 若保留，尽量带验证路径/失效条件**（作为**倾向**，不是必填字段）。
- ⏸️ **暂不定案（Open Design Question）**：是否需要把这些做成**五种可区分对象**、它们是 status 还是 enum、是否需要「验证路径/回归条件」这样的结构——**这些是实现时才能验证的，现在定为 schema 是过早。**

### 6.4 转化规则（定义的实质）

定义阶段的成功，**不是把所有项消到零**，而是让每一项落到它诚实的位置：

```
未知      → 尽量变成 位置（暂定 Assumption 或明确保留为 Unknown）
待办问题  → 已标注是否影响方向
推迟      → 显式、记得带回归条件
Assumption→ 尽量转成 Decision，或明确验证路径
稳定判定  → 剩余 Unknown 均属「可接受且可验证」，方向歧义已解决（见 2.2 张力声明）
```

## 7. 可信性 / Review 机制（压缩到第一版最小集）

> **重要（本次修订）**：初稿第 7 节的「最小可信机制集」其实大半不是最小。经 Red-Team 复核，**第一版真正需要的 Review/可信机制只有 4 条**；其余（MISS/EXTRA/ERROR 量化、独立审查 Agent、多轮纠错、来源标签强制）**全部标注为「以后加」，第一版不做。**

依据：PM 实证里保证可靠性的不是自动化 Review，而是「生成 → 人审 → 人对变更拍板」。同时，**探索阶段没有一份「上游已定的需求」可作对照基准，因此 MISS/EXTRA/ERROR 式「对照审查」在探索阶段不成立、应停用；它只在「定义/基线阶段」才有意义。**

### 7.1 第一版最小可信机制（4 条原则）

1. **已确认的进基线，且基线是唯一的正式定义来源**：被确认的内容有唯一落脚点，下游以它为准；探索中的内容不冒充已确认。
2. **研究 / 推断不自动成为决策，必须回到人**：研究结论、Agent 推理，在被人采用并确认前，都只是「候选」，不直接进基线。
3. **未验证的假设显式标出，不伪装成事实**：凡「我们还没验证但当作前提在用」的内容，用它的真实状态（暂定/未知）表达，而不是写成事实。
4. **基线变更走显式记录**：改动基线（含方向变化、范围变化、原决定被取代）时记录「改了什么、为什么改、依据是什么」，旧内容不删除且不假装仍有效。

> 第一版不做：独立自动 Review Agent、MISS/EXTRA/ERROR 三查量化、多轮自纠错、来源标签强制成存储字段。这些属于「看起来专业、但第一版可能不值得」的项，留待运行验证后再评估是否需要。

### 7.2 Review 放哪里（原则）

- **不是在每一层都自动做，而是在两个点停下来让人确认**：
  1. **定义模式完成、准备固化基线时**：把将要确认进基线的条目，交给用户过目，确认「这些确实是要定的吗」。
  2. **研究结论被采用前**：研究结果回到人面前，由人判断它是否改变定义。
- Review 的**价值**：提供一个与生成者不同的视角，检查「忠实（已谈定的是否都进基线）/ 诚实（有没有把未知编成确定）/ 越界（有没有把未定说成定了，或混入技术方案）」。**但这是「人审时问自己的三个问题」，不是一个独立审查框架。**
- 方向性 Open Question 出现时：提醒人它是否需要升级决策。
- **人的最终确认不可被任何自动化替代**。

## 8. 人机责任边界

### 8.1 Agent 可以自主完成什么

- 信息整理、归纳、结构化表达。
- 发现矛盾、提出问题、提醒盲区。
- 提出候选假设与候选方向（作为「待讨论」，不是「事实」）。
- 外部研究、检索已有工作、带回研究结论（**只作为讨论输入，不自动成为需求**）。
- 归纳候选定义（tentative），提交人确认。
- 一致性检查（候选是否与已知内容矛盾）。
- 起草基线初稿，供人审查修改。

### 8.2 Agent 不能替人决定什么（除非被显式委托，见 8.3）

- **项目方向**：要不要做这个方向、是否换方向。
- **项目范围**：上限/下限、做什么不做什么。
- **核心取舍**：多方案之间的价值权衡（含风险接受、限定条件下的优先级排定）。
- **成功标准**：什么叫做成。
- **重大决策**：放弃 / 收窄 / 重定义方向。

### 8.3 显式委托（本次修订新增，避免把 Agent 框死 / 把人打断疲）

哲学要求「让 Agent 在不牺牲控制权前提下最大化思考与执行效率」，也要求「不逐层确认」。为调和「Agent 不敢共创 → 频繁打断」与「Agent 越权夺权」这一对矛盾，第一版采用**显式委托**：

- 用户可以**显式授权** Agent 自行决定某类事项（例如「这个技术小选择你自己定」「这类边界你来判断」），此时责任上移，不再需要每步人盖章。
- 未获委托的方向 / 范围 / 核心取舍 / 成功标准，仍归人。
- 委托是**显式、可随时收回**的，且 Agent 对其自主决定仍应能给出依据（可溯源），只是不需要每次暂停等人。

> 这样既给了 Agent 真正的共创空间，又守住了「人掌方向」。第一版不追求自动判断「哪些该给人」，而是放手让用户显式划界。

### 8.4 触发人的时机（原则）

按**决策类型**触发（方向 / 承诺 / 成功 / 明确委托之外的大型取舍），不是「每几句问一次」，也不是「全部自动到不能再自动」。委托后对应类型跳过人工。

## 9. Baseline 定义

### 9.1 它是什么

Baseline 不是「最完整的 PRD」，而是**项目认知的稳定快照 + 后续工作的权威定义来源**。它的存在意义：当项目离开需求层进入技术阶段时，后续工作依赖的是「经过确认的项目定义」，而不是「某段模糊的对话记忆」。

### 9.2 它保存什么

- 要解决的问题与动机、方向与目标。
- Actor / Context / Environment。
- 边界：做什么 / 不做什么 / 现在不研究什么 / 推迟什么。
- 成功条件与验证方式。
- 约束。
- 概念契约（术语/关键概念定义）。
- 关键已有资产/上下文、中间参考材料（依据）。
- 确定性与不确定性：哪些确定 / 哪些暂定 / 哪些未知（分层诚实表达）。
- 重要内容的来源依据（可回溯）。

### 9.3 它不保存什么

- 具体技术选型、架构、模块拆分、类与接口、代码。
- 未经确认的推断（若保留，则显式标注为 Assumption / Open Question，而非决策）。
- 探索过程中的全部草稿与噪声（那是流动，不属于基线）。

### 9.4 它允许存在什么未知

**当然允许，并且鼓励诚实表达。** 个人/研究/工程项目的「未知」是天然合法的。Baseline 允许存在：分类清晰的 Unknown、Assumption（显式 + 尽量带验证路径）、Open Question（已标注是否影响方向）、Deferred（带回归条件）。它唯一不允许的是：**把不存在依据的未知，伪装成已确定的答案。**

### 9.5 它对后续技术阶段提供什么

- 一个明确、稳定、边界清晰的问题空间（做什么/不做什么/为什么/做到哪/现状）。
- 一个诚实的不确定地图：技术阶段可直接把 Assumption 当研究起点、把影响技术的 Unknown 当它自己的验证任务，而不是被蒙在鼓里。
- 一个概念契约：后续语言统一。

### 9.6 技术阶段应该如何理解它（本次修订弱化「唯一」）

- Baseline 是**唯一正式项目定义基线（权威定义）**：所有「我们已经决定的事实」，以基线的当前版为准。
- **但它不是技术阶段唯一能看的东西**：研究依据、原始材料、历史决策、未解决问题的上下文、概念契约的说明文本，技术阶段**仍可回溯查阅**。
- **修正依据**：哲学说的是「后续工作依赖确认过的项目定义，而不是模糊的对话记忆」——它反对的是「依赖未确认的模糊记忆」，**不是**「只看基线一个文件、看不到依据」。初稿把「不依赖对话记忆」升级成「后续阶段只依赖基线」是过强了，现修正为「基线是权威定义」「依据史可回溯」。
- 基线定义问题空间，不预决解空间——技术阶段在问题空间内自由做技术研究、选型、设计。
- 基线里的「未知」不是缺漏，是**移交**：技术阶段解决它们时，若发现「问题定义本身需要改」，应显式回环（见 4.4 / 第 3 节），而不是偷偷改基线。

### 9.7 什么情况下需要修订

- 出现改变方向/边界/目标的新信息（研究、用户想法变化）。
- 技术阶段暴露了「问题定义本身有误」，经人确认需要改。
- 原 Deferred 的回归条件被触发。
- 修订走**显式记录**：说明改动内容、原因、依据，且旧的失效内容显式声明被取代（不删除、不假装有效）。

## 10. 当前仍然开放的问题（Open Design Questions）

以下问题**现在没有足够证据决定**，刻意不在此强行定案，留给运行验证。

1. **「项目类型」是否作为一等维度。** 你的项目可以是产品/研究/实验/工程的混合体。是否需先定类型、再据此调探索自由度与边界语义，未验证。我倾向轻量区分，但不下定论。
2. **回环（探索→定义→再探索）触发的严格度。** 允许回环到什么程度完全自由 vs 设条件，需真实案例校准。
3. **「技术研究发现问题定义需改」与「技术研究正常推进」的分界。** 目前没有确切判据，这是需求层与技术阶段之间尚未解决的接缝。第一版先靠「显式回环 + 人确认」兜底，不设规则。
4. **Review 自动与人工的比例。** 我倾向「自动化只做视角提示、人最终裁判」，但自动化做到多细（是否需第二个独立视角的 Agent）需实践。**第一版先以人工审查为主**，自动化只做忠实性对照提示。
5. **是否要一套「个人方法/参考资料库」（个人版 KB）。** 依据不足，**建议第一版不做**——研究阶段由人直接提供资料即可。
6. **成功条件维度的可验证粒度。** 「可验证」是原则，具体长成什么（假设验证 / MVP 判定）需真实项目校准。第一版保留「成功=验证了什么假设、是否实现 MVP」的研究向表述，不强制可量化指标。
7. **确定性模型是否在实现中成为独立对象。** 见 6.3——当前只保留「一条确认度轴 + 溯源」的概念假设，是否成为数据模型由运行验证决定。

## 11. 比例原则（本次修订新增，最重要的一条）

> 这是 Red-Team 评审最重要的发现，也是第一版最该保留的原则：**治理重量必须随「方向不确定性 × 项目复杂度」调节。**

- **方向明确 + 小而简单**（如：给自己用的小工具）：需求层几乎可以退出。不需要 12 维、不需要探索/定义切换、不需要成功标准确认，可能只要「一句话目标 + 一条基线」。**任何治理都在损耗。**
- **方向模糊 + 中等复杂**（如：多 Agent 系统）：探索/定义切换、边界、未知表达开始有意义，使用少数关键维度。
- **方向模糊 + 研究/实验型**（如：需论文、假设验证）：探索、研究回环、诚实分层、Unknown 合法最重要；但**「稳定基线」本身要谨慎**——研究以「结论会变」为前提，过早稳定反而有害，此时 Baseline 更接近「明确研究问题 + 记录当前立场（可推翻）」。

**实现方式（原则层面）**：第一版应允许「用一个很轻的入口进入」，并根据**方向确定性 + 复杂度**自然决定用多少机制，而不是默认所有人走满流程。小项目应接近零流程，大且糊的研究项目才用完整模式。

**判定**：如果一个小项目也必须经历一套很重的治理，说明这套系统过度工程化了。**比例原则就是防这个。**

## 附：本 Blueprint 的设计原则（贯穿始终）

- 先定义问题，再定义信息。
- 先定义认知过程，再定义流程。
- 先定义职责，再定义 Agent。
- 先定义原则，再定义结构。
- 继承 PM 的方法论，不复制 PM 的领域结构。
- 可信性的锚点在人，自动化是辅助。
- **按不确定性与复杂度调节治理重量（比例原则）。**
- 第一版足够可靠即可，不为「专业感」过度工程化。
- 不为了形成完整设计，强行解决没有证据的问题。
- **概念模型不等于数据模型 / 持久化结构 / 文件。**
