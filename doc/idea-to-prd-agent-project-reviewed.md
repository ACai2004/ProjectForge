# Idea-to-Project Agent：从模糊意图到稳定项目定义

> 状态：理念重构版（Concept Review）
>
> 技术底座：Claude Agent SDK
>
> 核心定位：帮助一个人从模糊、开放、尚未完全成型的项目意图出发，通过持续对话、研究、澄清、质疑、重构与收敛，逐步形成一份经过确认的项目需求定义，并为后续技术设计、实现与迭代建立可靠基础。

---

## 1. 项目定位

本项目不是一个单纯的“PRD 生成器”，也不是把用户的一段自然语言一次性转换成一份漂亮文档。

它要解决的问题更早，也更根本：

> **当一个项目最开始只是一个模糊想法时，如何帮助人把这个想法逐渐想清楚、说清楚、研究清楚，并最终形成一个足够稳定、明确、诚实、可以进入后续工作的项目定义。**

因此，本项目关注的并不是“如何写出标准产品 PRD”，而是：

**如何让一个项目从模糊意图逐渐形成稳定的项目认知。**

最终文档只是这种认知在某个阶段的正式沉淀，而不是整个系统的核心目的。

这里的“项目”可以是产品、个人开发项目、工程项目、研究课题、实验性原型，也可以是这些类型的混合体。因此，它不应被企业产品管理语境下的 PRD 模型所限制。

---

## 2. 项目真正要解决的核心问题

从一个想法到一个真正可以开始做的项目，中间存在一段经常被忽略的过程：

> “我好像想做这个。”
>
> ↓
>
> “我真正想解决的是什么？”
>
> ↓
>
> “这个方向成立吗？”
>
> ↓
>
> “有没有已有工作？有没有更好的问题定义？”
>
> ↓
>
> “我们到底决定做什么？”
>
> ↓
>
> “做到什么程度？”
>
> ↓
>
> “哪些已经确定，哪些只是假设，哪些仍然未知？”
>
> ↓
>
> “现在是否已经足够明确，可以进入技术阶段？”

传统的需求生成系统往往默认项目已经基本成立，因此重点是把既有需求结构化。

而本项目需要处理的是更前面的状态：

**项目本身仍在形成。**

因此，它既不是单纯的需求收集，也不是单纯的信息检索，而是一个持续的：

**探索 → 研究 → 讨论 → 判断 → 重构 → 收敛 → 定义**

过程。

---

## 3. 项目的核心理念

### 3.1 从“文档生成”转向“项目认知形成”

本项目最重要的理念是：

> **文档是结果，不是目的；真正的目标是形成可靠的项目认知。**

如果在用户自己都没有想清楚的时候，Agent 只是快速生成一份结构完整的 PRD，那么形式上完成了任务，实际上可能只是把不确定性包装成了确定性。

因此，系统应该更重视：

- 问题是否真的被理解；
- 项目方向是否经过讨论；
- 关键判断是否有依据；
- 需求中的确定与不确定是否被明确区分；
- 项目边界是否真正被建立；
- 当前定义是否已经足够稳定，可以交给下一阶段。

---

### 3.2 开放探索与结构化收敛必须同时存在

本项目不应该在最开始就强迫用户填写一套固定字段。

因为真正有价值的项目往往需要先经历一段自由探索：

用户可以讲背景、想法、疑问、材料、观察、直觉甚至不成熟的判断；Agent 则可以理解、追问、挑战、比较、重构，并在必要时进行外部研究。

在这个阶段，系统的任务不是“尽快填满信息”，而是帮助思考向前推进。

当用户认为方向已经足够成熟，才逐步进入结构化的定义过程。

因此，本项目的基本交互思想不是：

**表单式需求采集。**

而是：

**开放探索 → 逐渐形成结构 → 明确确认 → 建立需求基线。**

---

### 3.3 Agent 应该能够挑战想法，而不仅仅是整理想法

在开放探索阶段，Agent 不只是一个秘书。

它可以：

- 指出逻辑矛盾；
- 提出不同的问题定义；
- 发现被忽略的假设；
- 提供替代方向；
- 通过研究外部资料改变对问题的认识；
- 帮助比较不同路径；
- 在必要时建议放弃、缩小或重构原来的想法。

这意味着项目允许 Agent 对“项目本身”产生认知上的影响。

但这种自由不是无限的。

一旦用户对某个方向作出明确决定，系统就应当进入更高的严谨度：后续定义必须忠实表达已经确认的决策，不能为了让文档看起来更完整而擅自改变它。

因此，本项目存在一个非常重要的原则：

> **探索阶段允许改变项目；定义阶段必须忠实于已经确认的项目。**

---

### 3.4 研究不是独立的附属步骤，而是探索能力的一部分

本项目中的研究不能被简单理解为：

> 先写 PRD，之后再做 Research。

很多时候，研究本身就会改变需求和方向。

例如，一个想法可能因为发现已有工作而被放弃，也可能因为新的论文、开源项目、技术资料或竞品信息而得到重新定义。

因此，研究应当能够与对话循环结合：

**Conversation ↔ Research ↔ Conversation**

研究的作用不是堆积资料，而是帮助项目形成更好的判断。

同时，研究的结果不应直接被当作“事实上的需求”，而应回到项目讨论中，由人和 Agent 一起判断它是否改变项目定义。

---

### 3.5 不追求“伪完整”，而追求“明确地知道自己不知道什么”

一个项目在需求阶段不可能知道所有事情。

尤其是个人项目、研究项目和实验性工程项目，很多内容本来就需要后续验证。

因此，系统不应把所有未知都当成需求缺失。

它需要能够区分：

- 已经确认的决定；
- 当前采用的假设；
- 尚未解决的问题；
- 需要进一步研究的问题；
- 暂时有意不做的事情。

换句话说：

> **“未知”本身可以是合法且有价值的项目状态。**

系统真正需要避免的不是“不完整”，而是：

**在没有依据的情况下制造确定性。**

---

## 4. 需求文档在本项目中的真正定位

本项目仍然可以产出需求层文档，并可以继续称为 PRD；但这里的 PRD 不应被理解成传统企业产品 PRD 的缩小版。

更准确地说，它是一份：

> **Project Requirement Definition / Project Requirement Baseline**

它的职责是建立一个供后续工作共同依赖的项目定义。

它应该能够回答：

- 我们为什么做这个项目；
- 项目到底要解决什么问题；
- 当前决定做什么；
- 不做什么；
- 在什么背景和场景下成立；
- 对关键行为与目标有什么基本共识；
- 什么是约束；
- 什么是成功；
- 哪些内容已经确定；
- 哪些内容仍然未知或需要验证。

它不应该在这个阶段提前替后续技术阶段决定具体技术路线、框架、数据库、服务拆分或实现细节。

因此：

> **需求阶段负责定义“我们要做什么、为什么做、做到哪里，以及目前知道什么”；技术阶段再回答“具体怎么做”。**

---

## 5. 与企业产品 PRD Agent 的根本区别

本项目会大量借鉴成熟的需求工程思想，但不会把企业产品 PRD 的结构直接搬过来。

两者的起点不同。

企业产品 PRD Agent 往往默认：

> 产品方向已经基本成立，现在需要把需求理解、补全、结构化并对齐。

而本项目面对的可能只是：

> 一个仍然模糊、甚至可能需要被推翻或重构的项目想法。

因此，两者的核心任务也不同：

**企业产品 PRD Agent：**
把已经存在的产品需求定义清楚。

**本项目：**
帮助项目本身逐渐形成，再把形成后的项目认知稳定地定义下来。

这带来几个重要区别：

- 企业产品场景更强调需求完整性、一致性与协作对齐；
- 本项目更强调探索、判断、方向形成与不确定性的诚实表达；
- 企业产品场景中的“未知”通常更多意味着需求缺口；
- 本项目中的“未知”可能本身就是当前阶段合理的开放问题；
- 企业产品 PRD 更偏向产品行为定义；
- 本项目的需求文档更偏向项目定义与后续工作的共同基线。

因此，参考企业 PRD Agent 时，真正应该继承的是它背后的：

**阶段化、信息治理、审查、决策门、可追踪、避免信息漂移等工程思想。**

而不是机械复制它的字段、术语和企业业务语义。

---

## 6. 本项目最重要的方法论：继承“原则”，重建“语义”

面对已有的 PRD Agent、工作流或 SOP，本项目不应该采用“直接改造模板”的思路。

更合理的思考方式是：

### 第一层：识别它解决的抽象问题

例如一个机制可能解决的是：

> 防止需求在阶段转换时丢失、变形或被偷偷添加。

这个抽象原则对本项目同样成立。

### 第二层：理解它为什么在原场景中这样实现

企业产品、个人项目、研究项目的对象不同，因此同一原则的具体实现形式可能不同。

### 第三层：在本项目语境中重新定义

最终继承的应该是：

**解决问题的原则。**

而不是：

**原项目的表面结构。**

因此，本项目不是一个“企业 PRD Agent 的个人版”，而应该是：

> **借鉴成熟需求工程思想，并针对个人项目、研究与工程探索重新构建的一套项目形成与定义机制。**

---

## 7. 阶段化的真正目的

本项目需要阶段，但阶段化并不是为了把流程做得复杂。

它真正解决的是：

> **不同阶段的人和 Agent，应该处于不同的认知状态，并承担不同的责任。**

在开放探索阶段，重点是：

**理解、发现、质疑、研究、重构。**

在需求定义阶段，重点转向：

**整理、明确、确认、建立边界。**

在后续技术阶段，问题进一步转向：

**研究实现路径、进行技术判断、形成技术设计。**

因此，阶段边界的价值不是“流程管理本身”，而是：

> **防止系统在还没有想清楚问题的时候就开始解决问题。**

同时也防止技术细节反过来过早绑架需求定义。

---

## 8. 人机协作的核心原则

本项目不是让 Agent 代替人做所有决策，也不是让人不停点击“确认”。

更合理的关系是：

> **Agent 负责推动认知过程，人负责关键方向性决策。**

Agent 可以主动：

- 组织问题；
- 发现矛盾；
- 进行研究；
- 提供判断依据；
- 给出候选方向；
- 提醒潜在风险。

但对于真正改变项目方向的判断，人仍然拥有最终决策权。

因此，人机协作的目标不是最大化 Agent 自主性，而是：

> **让 Agent 在不牺牲项目控制权的前提下，最大化思考与执行效率。**

---

## 9. 信息与决策的可信性

本项目需要特别重视一个问题：

> **项目在不断讨论和演进的过程中，信息会发生漂移。**

用户说过的话、研究发现的事实、Agent 的推断、暂时采用的假设、最终确认的决策，这些概念不能混在一起。

因此，本项目应该逐渐形成一种清晰的信息治理原则：

> **知道什么来自用户，什么来自外部依据，什么是 Agent 的推断，什么已经成为共同确认的项目定义。**

需求基线的价值就在于此：

当项目从探索状态进入下一阶段时，后续工作依赖的应该是经过确认的项目定义，而不是某一段模糊的对话记忆。

---

## 10. 项目的最终目标

本项目并不是为了证明“AI 能写 PRD”。

它真正希望建立的是一条可靠的项目形成链路：

> **模糊项目意图**
>
> → 开放探索
>
> → 研究与认知扩展
>
> → 问题澄清与方向判断
>
> → 项目逐渐收敛
>
> → 结构化定义
>
> → 人确认
>
> → 形成稳定的需求基线
>
> → 进入技术研究与设计
>
> → 进入实现与验证
>
> → 根据验证结果继续演化

其中最重要的变化不是“文档越来越长”，而是：

> **项目从“我大概想做这个”，逐渐变成“我们明确知道现在要做什么，以及为什么这样做”。**

---

## 11. 本项目的边界

为了保持理念清晰，本项目不应该把所有与项目开发有关的问题都塞进需求阶段。

需求阶段不负责提前完成：

- 具体技术选型；
- 具体框架与数据库决策；
- 详细系统架构；
- 类与接口设计；
- 具体代码实现；
- 部署方案等实现细节。

这些内容属于后续技术与实现过程。

同样，本项目也不应把“自动生成最终代码”定义成前半段存在的理由。

代码生成的价值在于证明：

> **经过充分探索与定义后的项目认知，能够可靠地传递给后续技术和实现阶段。**

---

## 12. 成功的真正含义

这个项目是否成功，不应主要看：

> 生成了多少页 PRD。

更重要的是：

> **一个原本模糊的项目，在经过人与 Agent 的共同工作之后，是否真正变得更清楚、更稳定、更可判断、更容易进入下一阶段。**

一份优秀的结果，不一定意味着所有问题都已经被解决。

它更应该意味着：

- 核心问题被说清楚；
- 项目边界被建立；
- 关键决策被明确；
- 重要假设没有被伪装成事实；
- 未知问题被显式保留；
- 后续技术工作有一个可信的起点。

---

## 13. 一句话定义

> **这是一个面向个人项目、研究与工程探索的 Agent 系统：它不只是把想法写成 PRD，而是通过对话、研究、质疑与逐步收敛，帮助人把一个模糊的项目意图发展成稳定、明确、可验证、可进入后续工作的项目定义。**

---

## 14. 当前阶段应当保持的设计原则

在真正开始实现之前，本项目首先应该保持这几个原则：

**不要过早被 PRD 模板定义。**

**不要把开放探索误解成字段收集。**

**不要把未知强行补成确定答案。**

**不要让技术实现过早反向决定需求。**

**不要把 Agent 的推断与人的最终决策混在一起。**

**不要把“文档生成”当成系统的最终目的。**

最重要的是：

> **先把“这个系统到底要帮助人完成什么认知过程”想清楚，再决定 Skill、Agent、Artifact、工作流和实现结构。**
